# Dirrio deployment

Dirrio uses ordinary Docker Compose files, with per-service deployment folders following Galliun's structure. No Bun wrapper or generated interpolation variables are needed. Images build from the repository checkout using Bun 1.3.14 and the committed lockfile. Convex and private R2 storage remain external managed services.

## Dokploy and root Compose

Set Dokploy's Compose path to `docker-compose.yml` at the repository root. Enter the values from the root `.env.example` in Dokploy's Environment editor, replacing development URLs with production HTTPS origins and providing server credentials. Dokploy writes `.env` next to the Compose file. No extra command, local per-service file, or prebuild script is required.

For a local deployment from the repository root, prepare `.env` without overwriting an existing configuration and run:

```sh
docker compose up --build -d
# Or:
podman-compose up --build -d
```

This starts API, worker, API nginx proxy, web, and admin. The root Compose file loads `.env` into API/worker through `env_file` and mounts it read-only at `/app/.env`. The mount preserves the application's explicit provider-key loading rules. The host file must be readable by the image's `bun` user; on Linux use an appropriate owner/group or ACL without making it world-readable. All environment files are excluded from image build contexts.

Both frontend builds use ordinary shared `VITE_CONVEX_URL` and `VITE_API_URL` arguments. Web additionally uses `VITE_ADMIN_URL`; admin uses `VITE_WEB_URL` and `VITE_APP_ENV`. If `VITE_CONVEX_URL` is unset, Compose uses `CONVEX_URL`. Other public URLs default to localhost for local container hosting. Production configuration must override them. Changing these values requires rebuilding the frontend images. Browser URLs must never be Docker service names. Public variables alone are passed as build arguments; server credentials remain runtime configuration.

The root stack shares API/worker configuration. There is no `deployments/.env` requirement. Root `.env` also supplies Compose interpolation, as generated by Dokploy. Never commit a populated `.env`.

## Per-service structure

```text
docker-compose.yml              Whole stack, run from repo root or Dokploy
.env.example                    Root runtime and public build configuration
deployments/
  docker-compose.yml            Whole stack with per-service runtime files
  api/                          Dockerfile, Compose, .env.example
  worker/                       Dockerfile, Compose, .env.example
  web/                          Dockerfile, Compose, nginx, .env.example
  admin/                        Dockerfile, Compose, nginx, .env.example
  proxy/                        API proxy image and configuration
  convex/                       Production Convex scripts and .env.example
  scripts/                      Optional validation, smoke and bootstrap tools
```

Each standalone service uses its own `.env`, just as in Galliun. Copy examples without overwriting existing files, then use standard Compose:

```sh
docker compose --env-file deployments/web/.env -f deployments/web/docker-compose.yml up --build -d
docker compose --env-file deployments/admin/.env -f deployments/admin/docker-compose.yml up --build -d
docker compose --env-file deployments/api/.env -f deployments/api/docker-compose.yml up --build -d
docker compose --env-file deployments/worker/.env -f deployments/worker/docker-compose.yml up --build -d
```

With Dokploy, select the corresponding standalone path and enter that service's example variables into its Environment editor. It creates `.env` alongside that selected file. The worker can run independently of the API; both use the shared server image and different commands.

For the alternative combined `deployments/docker-compose.yml`, configure `deployments/api/.env` and `deployments/worker/.env` and pass the frontend environment files explicitly:

```sh
docker compose --env-file deployments/web/.env --env-file deployments/admin/.env -f deployments/docker-compose.yml up --build -d
```

Shared `VITE_CONVEX_URL` and `VITE_API_URL` must match across those files. For one Dokploy stack use the root Compose file, which needs only Dokploy's generated root `.env`. Choose either standalone or combined deployment on a host to avoid port conflicts.

## Production preparation

1. Set HTTPS origins for API, creator web and admin. Set `SITE_URL` and `VITE_WEB_URL` to the creator origin, include creator/admin in `WEB_ORIGINS`, and point `CONVEX_URL` / `VITE_CONVEX_URL` at the same production deployment.
2. Configure private R2 credentials and CORS for the exact creator/admin origins; see [R2 setup](../docs/r2-storage.md). Keep public bucket access disabled.
3. Configure SMTP and enable `EMAIL_NOTIFICATIONS_ENABLED` for email-code login. Alternatively configure Google login in Convex; its callback is `https://<deployment>.convex.site/api/auth/callback/google`.
4. Optionally run `bun run deploy:check` to validate the root production configuration without printing secret values. `bun run deploy:check:services` checks the per-service layout instead. Neither command is required to invoke Compose, and neither changes secrets.
5. Prepare `deployments/convex/.env` separately for the optional Convex tooling. Run `bun run setup:convex-auth-keys`, preserving existing auth keys. Rotation requires the explicit `--rotate` option and invalidates sessions.
6. Back up Convex and run `bun run deploy:convex` before starting updated API/worker releases. The script checks the production key's target, syncs an allowlist of runtime flags, and deploys from `packages/backend`. Flag updates take effect before code deployment; coordinate changes. CLI diagnostics are suppressed to protect secrets; investigate failures in the dashboard. The command then deploys repository help articles from `content/help`; unresolved Admin-edit conflicts fail the release after functions have been deployed. Resolve them with `help:deploy` before enabling the release. Review regenerated bindings afterward.
7. Build/start with standard Compose or Dokploy. Configure generation callbacks at `https://<api-host>/webhooks/generation`. If enabling Polar payments, configure `/webhooks/polar`, distinct product IDs, production credentials, and matching API/worker/Convex flags. Sandbox balances cannot fund live providers. Payments and paywall default to disabled.
8. Run `bun run deploy:smoke`, then verify login, project access, uploads, media range playback, SPA deep links, worker heartbeat/restart recovery and browser export. The smoke command sends read-only HTTP probes and does not start paid work.
9. After the intended administrator signs in once, run `bash deployments/scripts/bootstrap-admin.sh you@yourdomain.com --reason "Initial platform administrator"`. This runs Dirrio's audited verified-account promotion inside the running root API container. For a standalone API stack set `COMPOSE_FILE=deployments/api/docker-compose.yml`; set `CONTAINER_ENGINE=podman` if using Podman.

Convex runtime receives only auth/OAuth configuration, `SITE_URL`, and the staging/payment flags. Provider, SMTP, R2, deployment and webhook credentials belong to API/worker only. Blank optional OAuth values do not delete remote credentials; remove retired secrets explicitly after verification.

## Operations and rollback

Use `docker compose ps`, `docker compose logs --tail 100`, and `docker compose down` directly from the repository root. Equivalent Podman commands work with the same files. Package `docker:*` and `podman:*` shortcuts invoke standard Compose commands without preprocessing.

Host ports default to loopback 8080 (web), 8081 (admin), and 8082 (API proxy); override `WEB_PORT`, `ADMIN_PORT`, and `API_PORT`. With Dokploy, route domains to port 80 of `web`, `admin`, and `api-proxy` using its domain configuration. The API application listens privately on 3001. Worker has no public listener. See [proxy notes](proxy/README.md) for HTTPS and forwarding requirements.

API readiness probes `/ready`; `/health` is process liveness. Worker health requires successful Convex heartbeats and recent polling or active tasks. Compose restart policies restart exited processes, not merely unhealthy ones; alert on stale/unhealthy workers. Do not reset uncertain provider submissions or financial holds to force progress. API drains requests before the 150-second stop deadline; worker handles SIGTERM. Logs rotate at 10 MB with three retained files.

Run deployment tests, typechecking, lint, application tests, production builds and container builds before release. Retain immutable `RELEASE_VERSION` image tags and secure backups of configuration, Convex and R2. Container filesystems do not back up managed data.

Deploy compatible Convex schema/functions first, API/worker second, frontends last. To roll back, pause admissions, stop the worker and reconcile accepted/uncertain provider jobs and reservations. Restore compatible previous images with `RELEASE_VERSION=<previous> docker compose up -d --no-build --pull never`. Review schema compatibility before restoring Convex functions; never blindly restore database snapshots or replay provider submissions.

## Help content deployments

`deploy:convex` includes the repository help import. For article-only releases use
`bun run help:deploy --environment production --env-file deployments/convex/.env`
to preview, then repeat with `--apply`. Both API and worker images also include the
content and importer for explicit container execution. Imports never run as a side
effect of API/worker startup. Manual articles are preserved and conflicting Admin
edits require an explicit per-article choice. See the [content deployment guide](../content/help/README.md).
